# Module A — RAG Docs Assistant

A retrieval-augmented generation (RAG) feature that answers natural-language questions grounded in real Express.js documentation, with sources shown for every answer.Module A is Generative AI, plainly and simply. Generative AI means: you give a model some input (text, an image, whatever), and it generates new content in response — a paragraph, an answer, a summary.

## What it does

Ask a question like *"how does routing work in express"* and get back an answer generated by an LLM, grounded specifically in the actual Express docs — not the model's general training knowledge — along with a list of which doc files the answer came from.

## Architecture

```
React (AskDocsPanel) → POST /api/ask → Express route:
  1. Embed the question (Voyage AI)
  2. Similarity search against Supabase/pgvector (match_docs_chunks)
  3. Build a grounded prompt from the retrieved chunks
  4. Generate the answer (Gemini)
  5. Return { answer, sources } → rendered in the UI
```

Three separate services, three separate jobs:
- **Voyage AI** — turns text into 1024-dimension vectors (embeddings). Chosen because Anthropic doesn't offer an embeddings model; Voyage is Anthropic's recommended partner and has a 200M free-token tier.
- **Supabase (Postgres + `pgvector`)** — stores every chunk alongside its embedding, and does the actual similarity search via a custom SQL function.
- **Gemini (`gemini-3.6-flash`)** — generates the final answer from the retrieved context. (Originally built against Claude/Haiku; swapped to Gemini after exhausting Anthropic's free credit — the swap only touched the generation step, nothing else in the pipeline changed.)

## Ingestion pipeline (`server/scripts/ingest.js`) — one-time, repeatable

Run once against a given corpus; re-run only if the source docs change or the chunking strategy changes.

1. **Read** all `.mdx` files from Express's official docs repo (cloned locally, English/5.x docs only — 16 files).
2. **Clean** each file: strip YAML frontmatter, strip stray Astro `import` statements, unwrap `<Alert>` component tags while keeping their text content.
   - Known accepted limitation: the import-stripping regex also removes `import` lines that appear *inside* fenced code examples (not just the Astro component imports it's meant to target). Left as-is — the LLM still answers correctly from its own Express knowledge even if a displayed code sample is missing one import line.
3. **Chunk** each file by `##` and `###` Markdown headings (not just `##`), trading a few more/smaller chunks for meaningfully more precise retrieval — a heading-heavy `## Route paths` section, for example, splits into its `### String paths` / `### Wildcards` / etc. sub-chunks instead of becoming one large, semantically diluted chunk. Result: 73 chunks from 16 files.
4. **Embed** each chunk via Voyage (`voyage-4-lite`, `outputDimension: 1024`), batched 10 at a time to respect the free tier's 3-requests-per-minute limit, with a retry-with-backoff wrapper around 429 (rate limit) errors.
5. **Store** each `{ content, source_file, embedding }` row in Supabase's `docs_chunks` table (Row Level Security enabled; only the backend's `service_role` key can access it, since RLS is bypassed by that key by default).

## Retrieval + generation (`server/src/routes/ask.js`) — live, per request

This route is "the RAG" in the strict sense — ingestion is just the data-prep step that makes this possible.

1. Embed the incoming question the same way chunks were embedded (same model, same dimension).
2. Call the `match_docs_chunks` Postgres function via `supabase.rpc(...)`, which ranks all rows by cosine distance (`embedding <=> query_embedding`) between the question's vector and every stored chunk's vector, returning the top 5.
3. Build a prompt that includes the retrieved chunks, numbered and labeled with their source file.
4. **The single most important line in the whole feature**: an explicit instruction telling the model to answer *only* from the provided context and say "I don't know" otherwise — this is what actually prevents hallucination; without it, the retrieval step would be decorative.
5. Return `{ answer, sources }` — `sources` is the deduplicated-in-spirit (not yet de-duplicated in code — a possible future polish item, since the same source file can appear more than once if multiple of its chunks rank in the top 5) list of filenames the answer was grounded in.

## The similarity search, in plain terms

Every embedding is a point in a 1024-dimension space. `pgvector`'s `<=>` operator computes the cosine distance (a measure of the *angle*, not just raw distance, between two vectors) between the question's point and every stored chunk's point. Postgres sorts all rows by that distance and returns the closest 5. At 73 rows this is a full brute-force comparison every time (fast enough to not matter); at real production scale, an approximate index (HNSW/IVFFlat) would be added to avoid comparing against every row — not needed here, but worth knowing the option exists.

## Frontend (`client/src/AskDocsPanel.jsx`)

A simple controlled form (question in, `POST /api/ask`, render `answer` and a `Sources` list from `answer.sources`) — no separate work needed here beyond the initial Phase 1 wiring, since the backend's response shape was designed to match what the UI already expected.

## What this demonstrates (for interviews / resume)

- Understanding of the full RAG pattern: chunking strategy trade-offs, embeddings, vector similarity search, grounded generation
- A concrete anti-hallucination guardrail (the "answer only from context" instruction) and source attribution in the UI — both directly answer the "appropriate controls and governance" language from the target job description
- Handling real-world failure modes: rate limiting with retry/backoff, swapping LLM providers mid-project with minimal blast radius, verifying assumptions (model names, embedding dimensions) against current docs instead of memory

## Known limitations / possible next steps

- `sources` isn't de-duplicated by filename (a question can list the same source file twice if two of its chunks both rank highly)
- The import-stripping regex doesn't distinguish between prose and fenced code blocks (documented above)
- No vector index yet — fine at 73 rows, would matter at real scale
- Ingestion currently depends on the Express docs being cloned to `/tmp`, which macOS periodically clears — fine for a one-off portfolio build, but not how you'd want a repeatable production ingestion job sourced
